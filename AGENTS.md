# AGENTS.md

Instructions for AI coding agents working **on the skanvil codebase**. Using skanvil inside a
skills library is different: that is what the `skanvil` agent skill covers
(`agent-skill/skanvil/SKILL.md`).

## What this project is

skanvil is a TypeScript (ESM) CLI and Node.js library, published to npm as `skanvil`. It creates,
validates, indexes, parametrizes, builds and syncs **libraries of Agent Skills**. A library is a
`skills/` folder of `SKILL.md` files plus a README index and a `.skanvilrc.json`. skanvil follows
the Agent Skills spec at https://agentskills.io/specification.

- `ARCHITECTURE.md`: module map, data flow and design decisions. Read it before structural changes.
- `CONTRIBUTING.md`: scripts, tests, conventions, how to add a rule, command or target, and releases.
- `docs/`: user documentation, one guide per topic.

## Commands

Run all of these before declaring a task done. CI runs the same checks on Linux and Windows with
Node 20, 22 and 24.

```bash
npm run lint           # ESLint
npm run format:check   # Prettier (npm run format to fix)
npm run typecheck      # tsc --noEmit over src/ and tests/
npm run build          # tsup → dist/, then schema.json
npm test               # vitest; bundles the CLI into tmp/cli-build first
```

- `npm run dev -- <command> [options]` runs the CLI from source, for example
  `npm run dev -- list -C ../some-library`.
- To try a command for real, create the library inside the gitignored `tmp/` folder or in the
  system temp folder, never in the repository root.

## Code layout and boundaries

- **`src/core/`** holds all behaviour. It never prints and never calls `process.exit`. Functions
  take a `Library` (or a path), return data and throw `Error`s whose messages a user can act on.
- **`src/commands/`** is a thin CLI layer: options → core call → text or `--json` output through
  `Output`. Every handler returns an exit code.
- **`src/cli.ts`** declares the commands with commander.
- **`src/index.ts`** is the public API. Export anything new that is useful programmatically.
- **`templates/`** is data: the library skeleton and the default skill. Changing how generated
  files look must not require code changes.
- **`agent-skill/skanvil/`** is the skill that teaches agents to use skanvil. It ships in the npm
  package.
- **`renderTemplate` and `resolveParamValues`** (`src/core/params.ts`) must stay
  **self-contained**: no imports, no outer variables, no helpers defined outside the function.
  `skanvil build` embeds their source with `Function.prototype.toString()`.

## Rules

1. **Tests for every behaviour change.**
   - Core behaviour goes in `tests/commands.test.ts`, on temporary libraries.
   - Pure helpers go in `tests/core.test.ts` or `tests/params.test.ts`.
   - Anything visible from the CLI (exit codes, `--json` shapes, TTY behaviour) goes in
     `tests/cli.test.ts`.
   - Wizard flows go in `tests/wizard.test.ts`, with mocked prompts.
   - Assert on files written to disk rather than on internals.
2. **JSDoc on every exported symbol.**
   - A summary, plus `@param`, `@returns` and `@throws`. Add `@example` for public entry points and
     `@remarks` for non-obvious behaviour.
   - These comments become the published `.d.ts`.
3. **Keep docs and the agent skill in sync with user-facing changes.** A new command, option, rule,
   JSON shape or config field must be reflected in:
   - `docs/` (`commands.md`, `validation.md`, `configuration.md`…);
   - the README command table when it applies;
   - `agent-skill/skanvil/SKILL.md` and `references/REFERENCE.md`.

   The test "the bundled skill passes skanvil's own default validation" must stay green. Never put
   a default placeholder string (such as the all-caps to-do marker) in the agent skill, not even as
   an example.

4. **Preserve user files exactly.**
   - Edit `SKILL.md` through `SkillFile`, which keeps YAML comments, quoting and untouched bytes.
   - Read and write README text through `Library`, which keeps CRLF.
   - Never rewrite a whole frontmatter or README when a targeted change works.
5. **Mutations must be safe.**
   - Compute all changes before writing.
   - Validate inputs (targets, parameters, categories) before the first write.
   - Roll back when a multi-step change fails, as `editSkill` does.
   - Never delete or overwrite files skanvil did not create: sync and `install-skill` check the
     manifest or version stamp.
6. **No new runtime dependencies without a strong reason.**
   - Pin majors that support Node ≥ 20.
   - Code generated by `skanvil build` must have zero dependencies.
7. **Cross-platform.** Use `path` for file system paths and `/` for paths shown in READMEs or
   manifests. Remember Windows: junctions for links, CRLF, `\` separators, and `displayPath()` for
   output.
8. **Style.**
   - Strict TypeScript, `node:` imports, no default exports, kebab-case file names.
   - Follow the existing patterns in a module before adding a new one.
   - All user-facing text, code comments and docs are in English.

## Commits and releases

- **Conventional Commits are mandatory.** release-please derives versions and the changelog from
  them:
  - `fix:` → patch;
  - `feat:` → minor;
  - `feat!:` or a `BREAKING CHANGE:` footer → major;
  - `docs:` is listed in the changelog without a release;
  - `chore:`, `refactor:`, `test:`, `ci:`, `build:` are hidden.
- **Never edit by hand** the `version` in `package.json`, `CHANGELOG.md`,
  `.release-please-manifest.json` or `v*` tags. Merging the release PR publishes to npm through
  Trusted Publishing.
- **Never commit** `dist/`, `tmp/`, `schema.json` or `skanvil_logo.jpg`, all of them generated or
  local. Do not commit or push unless the user asks.
